<objective>
Integrate the approval gate into the LangGraph pipeline and wire all Phase 8 alert components into TradingApp. The pipeline gets a new conditional route after risk_manager: below-threshold trades go directly to executor, above-threshold trades go to an approval_gate node that returns immediately with "pending_approval" status and spawns a background task for resolution.

Purpose: This connects the alert/approval infrastructure (Plans 01-02) to the core trading pipeline, enabling autonomous execution for small trades and human oversight for large trades. Also wires all Phase 8 components into the application lifecycle.

Output: Modified pipeline.py with approval gate, modified app.py with alert wiring, and unit tests.
</objective>

  1. Modify `src/trading/agents/pipeline.py`:

     a. Add imports:

     b. Add `approval_manager: Any = None` and `auto_execute_thresholds: AutoExecuteThresholds | None = None` fields to `PipelineDeps` dataclass.

     c. Create `_exceeds_threshold(assessment: dict, trade_proposals: list[dict], thresholds: AutoExecuteThresholds) -> bool` function:
        - Find the matching trade proposal for this assessment (match by `proposal_id` or symbol).
        - Check `abs(proposal.get("max_loss", 0)) > thresholds.max_loss_dollars`.
        - Check `abs(proposal.get("delta_impact", proposal.get("delta", 0))) > thresholds.max_delta_impact`.
        - Check `abs(proposal.get("vega_impact", proposal.get("vega", 0))) > thresholds.max_vega_impact`.
        - If any check exceeds, return True.
        - If proposal not found, return True (safe default: require approval if unknown).

     d. Modify `route_after_risk` to become a three-way conditional:
        - If no approved assessments: return END (unchanged).
        - If `deps.auto_execute_thresholds` is None or `deps.approval_manager` is None: return "executor" (no approval gate configured, backward compatible).
        - Check each approved assessment against thresholds using `_exceeds_threshold`. If ANY exceeds: return "approval_gate".
        - Otherwise: return "executor" (all below threshold, auto-execute).
        - Note: Since `route_after_risk` is a plain function and needs access to deps, change it to receive deps via closure binding (same pattern as node functions -- bind deps in `create_pipeline`).

     e. Create `_approval_gate_node(state: PipelineState, deps: PipelineDeps) -> dict`:
        - Generate approval_id: `f"approval-{state.get('run_id', uuid.uuid4().hex[:8])}"`.
        - Build context dict with: symbol(s), strategy_type, max_loss, max_profit, delta/theta/vega impact, timeout_minutes. Extract from approved assessments and trade_proposals.
        - If `deps.approval_manager` is None: log warning, return `{"approval_status": "approved", "approval_id": ""}` (fallback: auto-approve if manager missing).
        - Spawn background task via `asyncio.create_task(_await_approval_and_execute(approval_id, context, state, deps))`.
        - Return immediately with `{"approval_status": "pending_approval", "approval_id": approval_id}`. This allows the pipeline graph invocation to complete without blocking.

     f. Create `async _await_approval_and_execute(approval_id: str, context: dict, state: PipelineState, deps: PipelineDeps) -> None`:
        - `result = await deps.approval_manager.request_approval(approval_id, context)`
        - If `result == "approved"`:
          - Log "approval.granted", call `_executor_node(state, deps)` directly.
          - NOTE: Do NOT publish `alerts:trade_executed` here. The `_executor_node` (step i) already publishes `alerts:trade_executed` on successful execution, which covers both the direct-execution and post-approval paths. Publishing here would cause a double-publish.
        - If `result == "rejected"` or `result == "timed_out"`:
          - Log "approval.rejected" or "approval.timed_out".
          - Publish to `alerts:trade_rejected` with reason.
        - Wrap entire function in try/except -- errors must not crash the background task. Log errors as warnings.

     g. Update `create_pipeline` to add the approval_gate node and modify routing:
        - Add node: `workflow.add_node("approval_gate", lambda state: _approval_gate_node(state, deps))`
        - Change `route_after_risk` binding to use a closure that captures deps: `_make_route_after_risk(deps)` returns a function.
        - Add edge: `workflow.add_edge("approval_gate", END)` (approval gate returns immediately; background task handles the rest).
        - Update conditional_edges for risk_manager to use the new three-way router that can return "executor", "approval_gate", or END.

     h. Update `run_pipeline` initial_state to include `approval_status: ""` and `approval_id: ""`.

     i. Add alert event publishing to `_executor_node`:
        - After successful execution, publish to Redis: `await deps.redis_client.publish("alerts:trade_executed", json.dumps({"symbol": ..., "action": ..., "fill_price": ..., "quantity": ..., "run_id": ...}))`.
        - On execution failure or rejection, publish: `await deps.redis_client.publish("alerts:trade_rejected", json.dumps({"symbol": ..., "reason": ..., "run_id": ...}))`.
        - Guard with `if deps.redis_client:` to avoid error when redis not configured.

     j. Add alert event publishing to `_risk_node`:
        - When proposals are rejected for risk violations (i.e., assessments with `approved == False`), publish: `await deps.redis_client.publish("alerts:risk_breach", json.dumps({"symbol": ..., "violations": [...], "run_id": ...}))`.
        - Guard with `if deps.redis_client:` to avoid error when redis not configured.

     k. Modify `src/trading/risk/circuit_breaker.py`:
        - NOTE: Do NOT add a new `redis_client` parameter. CircuitBreaker already has a required `redis` parameter in `__init__` that assigns to `self._redis`. Use the existing `self._redis` directly.
        - In `_activate_halt`, after setting halt state, publish: `await self._redis.publish("alerts:circuit_breaker", json.dumps({"halt_type": halt_type, "reason": ..., "timestamp": ...}))`.
        - Wrap publish in try/except (non-fatal, log warning on failure).
